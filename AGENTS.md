# AGENTS.md

Guidance for coding agents working in the `trollimage` repository.

## What this project is

`trollimage` is the [Pytroll](https://pytroll.github.io/) imaging library: it turns scientific
2D/3D arrays into images, applies enhancements (stretches, gamma, colorization, palettization),
and writes the result to GeoTIFF/PNG/JPEG and friends.

**Who uses it.** Today the library is consumed primarily through
[Satpy](https://github.com/pytroll/satpy), which pins `trollimage>=1.24`. Satpy's two entry points
are `XRImage` (constructed in `satpy/enhancements/enhancer.py`, in `get_enhanced_image()`) and
`Colormap`. A much older generation of Pytroll — Satpy's predecessor, mpop — used the
`trollimage.image.Image` class instead. That class is still present and still tested, is *not*
formally deprecated (there is no `DeprecationWarning` in `trollimage/image.py`), and Satpy still
imports two free functions from it: `rgb2ycbcr`/`ycbcr2rgb` in `satpy/composites/resolution.py`.
Treat `image.py` as legacy-but-supported, and prefer `xrimage.py` for anything new.

## Module map

| Module | Lines | What it is |
| --- | --- | --- |
| `trollimage/xrimage.py` | ~1680 | `XRImage`: the xarray/dask image class. Stretches, mode conversion, saving. The modern API. |
| `trollimage/_xrimage_rasterio.py` | ~260 | Every line of rasterio-touching code (`RIOFile`, `RIODataset`, CRS/transform extraction). Imported only from inside function bodies, which is how rasterio stays optional. |
| `trollimage/colormap.py` | ~1310 | `Colormap` plus module-level `colorize`/`palettize`/`colorbar`/`palettebar`. Roughly 500 of those lines are built-in ColorBrewer colormap literals, constructed eagerly at import; `load_colorbrewer_colormaps.py` at the repo root is the script that generated them. |
| `trollimage/_colorspaces.pyx` | ~530 | Cython colorspace kernels (rgb / xyz / lab / lch / luv), fused `float32|float64`, `nogil`. Derived from `rio-color` — see `LICENSE_RIO_COLOR.txt`. |
| `trollimage/colorspaces.py` | 3 | Re-export shim for `rgb2lch`, `lch2rgb`, `convert_colors`. The old pure-Python implementation was deleted (commit `7ee58cb`). **Import through this shim, not `_colorspaces` directly.** |
| `trollimage/image.py` | ~1120 | Legacy masked-array `Image` class, plus `check_image_format()` (which `xrimage.py` still imports) and `rgb2ycbcr`/`ycbcr2rgb`. |
| `trollimage/utilities.py` | ~110 | `cmap_from_text`, `pilimage2trollimage`. Currently untested. |
| `trollimage/version.py` | — | Generated by versioneer. Never edit. |

## Dependency rules

- **Hard runtime dependencies:** `numpy` and `pillow` only. `python_requires = ">=3.11"`.
- **`xarray` + `dask`** are declared as an optional `xarray` extra, but they are module-level
  imports in `xrimage.py`. In practice they are required for anything involving `XRImage`.
- **`rasterio` is genuinely optional**, and the pattern used to keep it that way is the one to
  copy: all rasterio code lives in `_xrimage_rasterio.py`, that module is imported *only* from
  inside function bodies (`XRImage.rio_save` and its helpers), and `XRImage.save` catches
  `ImportError` and falls back to `pil_save` with a warning.
- `numexpr` is optional via the older module-level `try/except ImportError` idiom in `image.py`;
  it is used in exactly one place (`Image.gamma`).
- `pyproj` and `pyresample` are test-only. Production code never imports them — it duck-types
  `data.attrs["area"]` in `_xrimage_rasterio.get_data_arr_crs_transform_gcps`.
- There are **no import cycles**. `colormap.py` knows nothing about either image class; both image
  classes accept a duck-typed colormap argument. `colormap.py` does have an unconditional,
  import-time dependency on the compiled `_colorspaces` extension (through the shim), because
  color interpolation happens in LCh rather than RGB.

## Building for development

The package contains a compiled Cython extension, so an editable install alone is not enough —
after any change to `_colorspaces.pyx` the extension must be rebuilt in place:

```bash
pip install --no-deps -e .
python setup.py build_ext --inplace --cython-coverage --force
```

This is exactly what CI does, and the two-step split is deliberate: passing `--cython-coverage` to
pip as a `--build-option` forces a non-wheel build that is far too slow (see the comment in
`.github/workflows/ci.yaml`). Drop `--cython-coverage` if you do not need Cython line coverage.

Note that the build and lint tools are **not** in `install_requires` or in the `tests` extra — a
plain `pip install trollimage[tests]` environment has no `Cython` and no linter, so the commands
above will fail there with `ModuleNotFoundError` / `command not found`. `pre-commit` is
deliberately absent from `continuous_integration/environment.yaml` too: that file drives ten conda
solves in CI, and pre-commit pins its own ruff. Install it separately (`pip install pre-commit`). The full development
environment is `continuous_integration/environment.yaml`:

```bash
conda env create -n trollimage-dev -f continuous_integration/environment.yaml
```

Versioning is handled by **versioneer** (`tag_prefix = "v"`, config in `pyproject.toml`). The
root `.bumpversion.cfg` is stale — it still says `1.5.7` — and is not part of the release process.

## Testing

```bash
pytest trollimage/tests
```

Things that will bite you if you do not know them:

- **Warnings are errors.** `pyproject.toml` sets `filterwarnings = ["error", ...]` with a short
  list of targeted ignores, each carrying a comment about when it can be dropped. Any new warning
  emitted by library or dependency code fails the suite. If you add an ignore, add the comment too.
- `--strict-markers`, `--strict-config`, and `xfail_strict = true` are on. Unknown markers and a
  passing `xfail` are both failures.
- **There is no `conftest.py`, and the suite defines zero `@pytest.fixture`s.** Shared setup is
  done with plain module-level helper functions, class attributes, and `setup_method`/`setUp`.
  Cross-test helpers live in `trollimage/tests/utils.py` — notably
  `assert_maximum_dask_computes()`, the context manager used to assert that an operation stays
  lazy. Use it whenever you touch dask code paths.
- **Do not build dask arrays out of delayed objects.** To wrap a non-dask-friendly function, use
  `da.map_blocks` / `da.map_overlap` / `da.blockwise`, not `dask.delayed` + `da.from_delayed`.
  Modern dask pays a real performance penalty for mixing delayed objects with dask arrays, and Pytroll
  projects are migrating away from the pattern.
  This does **not** apply to the lazy *return* value of `XRImage.save(compute=False)`, which is the
  intended API for deferred writing. Note that it is deliberately not a `Delayed`: `pil_save`
  returns a dask array and `rio_save` returns a `(sources, targets)` pair for `da.store`. Moving
  off `Delayed` was the 1.27.0 change that Satpy still carries version shims for.
- Style to imitate: `test_colormap.py` is the most modern file (plain pytest classes, heavy
  `parametrize`, `tmp_path`, extracted assertion helpers). `test_xrimage.py` is a mix of old and
  new. `test_image.py` is `unittest.TestCase`-era and should not be used as a model.
- Known coverage gaps: there is **no test module for `colorspaces`/`_colorspaces`** (it is
  exercised only indirectly, through one rgb↔lch round trip in the colorize tests) and none for
  `utilities.py`.
- `test_save_jp2_int` needs a GDAL build with the `JP2OpenJPEG` driver. Without it the test fails
  with `DriverRegistrationError`, which is an environment problem, not a regression — the CI conda
  environment installs `libgdal-jp2openjpeg` for exactly this reason.

## Linting and style

Linting is **ruff**, run through pre-commit. `pyproject.toml` is the only lint config.

```bash
pre-commit run --all-files    # the canonical entry point; installs its own pinned ruff
ruff check .                  # only if ruff is installed in your environment
ruff format .
```

- `line-length = 120`, in `[tool.ruff]`.
- **`ruff format` is authoritative.** Do not hand-format, and do not fight it. Quote style is
  owned by the formatter, which is why the rule set deliberately does not select `Q`.
- **Every module, class, method, and function needs a Google-style docstring — including test
  methods.** Note that Google style needs the colon: `name (type): description`. An entry written
  as `name (type)` with the description on the next line is not parsed as a parameter at all, and
  `D417` will report the parameter as undocumented. Docstrings are rendered by
  `sphinx.ext.napoleon`.
- `_colorspaces.pyx` is linted by **cython-lint**, since neither flake8 nor ruff reads `.pyx`.
  After editing it, rebuild the extension and re-run the suite before trusting a green lint.
- Rule families that are deliberately *not* enabled (`ANN`, `N`, `PTH`, `UP031`, `RUF005`) are
  listed with reasons in `[tool.ruff.lint]`. Each is a planned standalone pass. **Do not widen the
  rule set inside an unrelated change** — that is what those comments are there to prevent.
- Two `max-complexity`/per-file-ignore entries are deliberate ratchets tied to other specs; the
  comments say which spec retires them.
- There is no mypy hook. `py.typed` ships, but only `xrimage.py` is meaningfully annotated.
- **pre-commit.ci enforces the hooks** on every pull request; the `ci:` block at the bottom of
  `.pre-commit-config.yaml` configures it. There is deliberately no lint job in
  `.github/workflows/ci.yaml` — that would just duplicate it.
- The tree was reformatted wholesale once. To keep `git blame` readable locally:

  ```bash
  git config blame.ignoreRevsFile .git-blame-ignore-revs
  ```

  GitHub applies that file automatically.

## Documentation

```bash
cd doc && make html      # output in doc/_build/html
```

- `doc/api/*.rst` is generated at build time by `sphinxcontrib-apidoc` and is gitignored. Never
  hand-edit those files.
- `doc/conf.py` loads a **local custom Sphinx extension**, `doc/trollimage_colormap.py`, which
  provides the `trollimage_colormap` directive that renders colormap swatch PNGs into
  `doc/_static/colormaps/` during the build.
- `conf.py` imports `trollimage` to get the version, so the package must be installed and the
  extension built before docs will build.
- Read the Docs builds with `fail_on_warning: true` (`.readthedocs.yml`). A Sphinx warning breaks
  the docs build.

## The public API other projects depend on

`trollimage` is a library with a real downstream consumer, and Satpy reaches fairly deep. Breaking
any of the following requires coordinating with Satpy:

- `XRImage`: `__init__`, `.data` (both read **and assigned** — Satpy replaces the DataArray in
  place), `.mode`, `.palette`, `.save`, `.finalize`, `.stretch`, `.gamma`, `.invert`, `.colorize`,
  `.palettize`, `.convert`, `.final_mode`, `.apply_pil`, `.pil_image`, `.putpalette`, `.show`,
  `.get_scaling_from_history`.
- **`XRImage._scale_to_dtype`** — private, but called directly by `satpy/writers/ninjogeotiff.py`.
- `trollimage.xrimage.invert_scale_offset` — used by `satpy/writers/ninjotiff.py`.
- `Colormap` and its constructors `from_file`, `from_sequence_of_colors`, `from_name`,
  `from_array_with_metadata`, plus `reverse`, `set_range`, `set_alpha_range`, `colorize`,
  `palettize`, `to_csv`, `to_rio`. Named built-in colormaps are resolved by *string* through
  `Colormap.from_name` from Satpy YAML, so renaming one is a breaking change.
- `trollimage.image.rgb2ycbcr` / `ycbcr2rgb`.

`XRImage.save`'s **return type** deserves special care: Satpy carries explicit version-branching
shims for the change made in trollimage 1.27.0 (see `_trollimage_res_to_satpy_res` in
`satpy/writers/geotiff.py` and the comments in `satpy/writers/simple_image.py`). Changing it again
has a real downstream cost.

## Conventions and gotchas

- **Mode is derived, not stored.** `XRImage.mode` is `''.join(self.data['bands'].values)`. To
  change an image's mode you change the `bands` coordinate.
- **`self.data` is always a dask-backed `xr.DataArray`** with dims `bands, y, x`. `__init__`
  normalizes dims and wraps numpy input via `da.from_array`.
- **Enhancements mutate in place and record history.** `stretch`, `gamma`, `invert`, `colorize`,
  `palettize`, etc. assign to `self.data` and append a dict to `attrs['enhancement_history']`.
  That history is read back later by `get_scaling_from_history` (for GDAL scale/offset tags) and
  by the geotiff colormap tag. Any new enhancement should append to it.
- **xarray drops `attrs` on many operations**, so several methods save `attrs` to a local and
  restore them at the end (`_scale_to_dtype`, `_add_alpha`, `finalize`, `crude_stretch`, `gamma`,
  `invert`). Preserve that when editing those methods.
- **There are three different representations of "missing" data**, and converting between them is
  most of what `finalize()` does: `NaN` for float data, an `attrs['_FillValue']` for integer data,
  and an alpha band. Order of operations matters and is currently only documented in comments —
  alpha is created *before* scaling, the fill value is substituted *after* scaling so it is not
  itself scaled.
- The `save`/`finalize` code path in `xrimage.py` is known to be hard to follow; it grew over many
  years of changing requirements. Change it carefully and prefer adding tests first. A rework is
  planned.
